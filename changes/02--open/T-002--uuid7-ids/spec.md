# T-002 Time-ordered UUIDv7 ids: spec

## Requirements

### New ids

- **R1** `new_id()` returns a new UUIDv7 as a 36-character string (`str(uuid.uuid7())`); ids created one after another in a process compare in creation order.
- **R2** `new_id` is importable from `commons.database` (as the intent says) and from a module without dependencies, so that `commons.users` and `jobs` can use it; importing `commons.users` before `commons.database`, or the other way round, keeps working.

### Where ids are generated

- **R3** `EntityMixin.id` defaults to `new_id()`.
- **R4** In `commons.users`, the default ids of `User.id_`, `RegisteredUser.id_` and role assignments, and the ids of users created in code without an id (`user.py`, 5 places), come from `new_id()`; an id passed in explicitly is kept as given.
- **R5** New job ids in `jobs` come from `new_id()`; an id passed in explicitly is kept.
- **R6** `Event.event_id` defaults to `new_id()`; the private `_new_event_id` of `commons.events` is removed.
- **R7** Login request ids, real and fake, stay `uuid4().hex`.

### Compatibility and documentation

- **R8** No column, type or length changes: stored ids stay valid and readable; no data migration.
- **R9** The comment in `column_lengths.py` and the documentation name UUIDv7 for new ids; `new_id` is in the API reference; `poe check` and `poe docs-build` pass.

## Design

### Where `new_id` lives

`commons.database` imports `commons.users` (`unit_of_work.py`, `unit_of_work_sql.py`, `history.py`), so `commons/users/user.py` can't import from `commons.database` without a cycle: importing `commons.users` first would load `commons.database`, which imports `commons.users.User` before it exists.

So `new_id` is defined in a new leaf module `commons/id_operators.py`, following the `*_operators` modules (`datetime_operators`, `string_operators`, …), with no imports but `uuid`:

```python
from uuid import uuid7


def new_id() -> str:
    """Return a new id: a time-ordered UUIDv7 as a 36-character string."""
    return str(uuid7())
```

`commons.database` re-exports it next to `ID_LENGTH`, as the intent promised; `commons.users`, `jobs` and `commons.events` import it from `commons.id_operators`. `commons/__init__.py` lists `id_operators` like the other operator modules.

### Call sites

| Place | Today | After |
| --- | --- | --- |
| `commons/database/entity.py` `EntityMixin.id` | `lambda: str(uuid4())` | `new_id` |
| `commons/users/user.py` lines 275, 567, 644 (defaults) | `lambda: str(uuid4())` | `new_id` |
| `commons/users/user.py` lines 350, 774 (`id or …`) | `str(uuid4())` | `new_id()` |
| `src/jobs/jobs.py` line 48 | `str(uuid4())` | `new_id()` |
| `commons/events/event.py` | `_new_event_id` | `new_id` |
| `commons/users/login_tokens/service.py` | `uuid4().hex` | unchanged (R7) |

### Documentation

`docs/api/id-operators.md` (`::: commons.id_operators`) in the "General" section of the `nav`, like the other operator modules; the comment in `column_lengths.py` reads "36-char UUID strings (new ones UUIDv7, see `commons.id_operators.new_id`)".

## Alternatives considered

- **Define `new_id` in `commons.database`** (the intent's wording; changed while specifying, it is re-exported there instead): causes the import cycle above; it would need a lazy import inside the default factories of `user.py`, which hides the dependency.
- **Move `User` out of `commons.users` or break the `database` → `users` dependency:** a larger refactoring of public modules for one function.
- **A private helper per package:** the intent asks for one public function.

## Constraint mapping

| Constraint (intent) | Met by |
| --- | --- |
| Not breaking: `new_id()` is an addition, ids keep type, length and columns | R1, R2, R8 |
| No new dependency | R1 (standard library `uuid.uuid7`) |
| Ids that act as hard-to-guess handles don't become guessable | R7 |

## Open questions

None.

## Areas of concern

1. **Import cycle** (R2): the order in which `commons.users` and `commons.database` are imported must not matter. Handled by a test that imports each first in a fresh interpreter. Owner: Michael Wellner.
2. **Apps relying on random ids** (R3–R5): an app that used an id as a secret (e.g. in an unguessable URL) gets ids that reveal their creation time and have 74 random bits instead of 122. Not seen in `commons`; apps on `versions/1` should check before upgrading, mentioned in the PR. Owner: Michael Wellner.

## Out of scope

- Login request ids (R7), stored ids and id columns (R8).
- Ids generated by the apps themselves; they can use `new_id()` in their own changes.
