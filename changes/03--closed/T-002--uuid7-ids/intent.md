# T-002 Time-ordered UUIDv7 ids

## Problem

`commons` generates its ids with `uuid4`, so they are random: primary keys of new rows land anywhere in the index (page splits and fragmentation, especially on SQL Server clustered keys), and an id says nothing about when or in which order its object was created. With Python 3.14 (T-001), `uuid.uuid7` is in the standard library, and the events of T-001 already use it; the rest of `commons` still doesn't, and each place builds its id inline.

Today, ids are generated in:

- `commons.database.EntityMixin.id` (every operational entity table of the apps).
- `commons.users`: users (`User.id_`, `RegisteredUser.id_`), role assignments, and the ids given to users created in code (`user.py`, 5 places).
- `commons.users.login_tokens`: login request ids (`uuid4().hex`, 32 hex characters), also as fake ids for unknown addresses and rate-limited requests.
- `jobs`: job ids (`src/jobs/jobs.py`).
- `commons.events`: event ids, already UUIDv7 (private `_new_event_id`).

## Proposed outcome

- New ids of entities, users, role assignments and jobs are UUIDv7 strings (36 characters), time-ordered, generated by one public function `new_id()` in `commons.database` (next to `ID_LENGTH`); apps can use it for their own ids.
- Event ids use the same function instead of the private helper of `commons.events`.
- Existing ids stay valid and unchanged: same 36-character form, same columns, no data migration.
- Login request ids stay `uuid4().hex`: they are handles a client keeps to redeem a 6-digit code, also handed out as fakes for unknown addresses; UUIDv7 would reveal their creation time and cut their random bits from 122 to 74, for no gain.
- Not part of this change: changing stored ids, or the id columns.

## Affected users and systems

- **`lib--python-commons`:** the id defaults above; `column_lengths.py`'s comment ("36-char uuid4 strings"); docs and tests that mention `uuid4`.
- **Apps on `versions/1`** (`app--beleglotse`, `app--cross-border-rules` once on 3.14, `lib--conversations` after its migration): new rows get UUIDv7 ids; nothing to change in their code.
- **Apps on `versions/0`:** unaffected.

## Constraints

- Not breaking (`feat`): `new_id()` is an addition, and ids keep their type (`str`), length (36) and columns; code that treats ids as opaque strings keeps working.
- No new dependency: `uuid.uuid7` of the standard library (Python 3.14).
- Security: ids that act as hard-to-guess handles must not become guessable or reveal more than today.
